# vulncheck

Консольный инструмент для проверки версий программных продуктов на известные
уязвимости. Решает тестовое задание: спроектировать базу данных по двум фидам,
занести в неё данные и построить по ним CLI, который

- по названию продукта выводит версию без уязвимостей;
- по названию продукта и версии выводит информацию об уязвимостях.

## Технологии

Python 3.12, SQLAlchemy 2, Pydantic 2, argparse, SQLite. Тесты: pytest.
Линтер и форматирование: ruff. Зависимости: uv (или pip).

## Структура проекта

```

│   ├── services/
│   │   ├── loader.py              загрузка фидов в базу

```

## Исходные данные

- `data/versions.json`: производитель, продукт, версия (834 записи).
- `data/vulnerabilities.json`: производитель, продукт, номер бюллетеня (`KLA_id`),
  описание, дата публикации, первая уязвимая версия, первая исправленная версия
  (135 записей, 24 продукта).

Фид версий содержит все известные версии, в том числе уязвимые. Фид уязвимостей
описывает диапазоны уязвимых версий. Безопасные версии получаются сравнением:
это версии продукта, не попавшие ни в один диапазон.

## Установка

Нужен Python 3.12+. Есть два способа.

Через uv:
```
uv sync
```
Команды запускаются как `uv run vulncheck ...`.

Через pip:
```
python -m venv .venv
.venv\Scripts\activate          # Windows; на Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
```
После этого доступна команда `vulncheck ...` без `uv run`. Для разработки
(тесты и линтер) вместо этого `pip install -r requirements-dev.txt`.

## Использование

Команды запускать из корня проекта: пути `data/` и файл базы `kasp.db`
считаются от текущей папки. В примерах команды записаны без `uv run`; при
установке через uv добавляйте его перед командой.

В репозитории лежит готовая база `kasp.db` с загруженными данными, поэтому
`safe` и `check` можно запускать сразу. Команда `load` нужна, чтобы создать
базу заново или догрузить новые данные.

### Загрузка данных

```
vulncheck load
```
```
versions.json: добавлено 834, уже было 0, ошибок 0
vulnerabilities.json: добавлено 135, уже было 0, ошибок 0
```
Повторный запуск безопасен: существующие записи пропускаются, новые добавляются.
Некорректные записи не загружаются, их список выводится в stderr. Свои файлы:
`vulncheck load --versions путь.json --vulns путь.json`.

### Версия без уязвимостей

```
vulncheck safe "Apache Tomcat"
```
```
Продукт: Apache Tomcat (Apache Software Foundation)
  Последняя безопасная версия: 10.0.27
```
Флаг `--all` выводит все безопасные версии. Название ищется без учёта регистра:
сначала точное совпадение, затем по части названия (`vulncheck safe vlc` покажет
оба продукта VLC).

### Проверка версии

```
vulncheck check "Apache Tomcat" 9.0.50
```
```
Продукт: Apache Tomcat (Apache Software Foundation), версия 9.0.50
  Найдено уязвимостей: 10

  KLA78283  2024-12-09
    Описание: Multiple vulnerabilities in Apache Tomcat
    Уязвима с: 9
    Исправлено в: 9.0.98
  ...
```
Уязвимости идут от новых к старым. Возможные исходы:

| Ситуация | Вывод |
|---|---|
| версия есть в данных и попадает в диапазон | список уязвимостей |
| версии нет в данных, но она попадает в диапазон | список уязвимостей и пометка «Версии нет в списке известных версий» |
| версия есть в данных, уязвимостей нет | «Уязвимостей не найдено» |
| версии нет в данных, уязвимостей нет | «Версия не найдена в данных» |

### Коды возврата

- 0: успех;
- 1: продукт не найден, база пуста, некорректная версия или файл, при загрузке
  пропущены невалидные записи;
- 2: неверные аргументы командной строки.

## Принятые решения

- Диапазон уязвимости это полуинтервал `[start, fixed)`: версия `fixed` уже
  исправлена.
- Версии сравниваются как числа, а не как строки: `10.0.9` меньше `10.0.23`.
  Нули в конце не важны, `15`, `15.0` и `15.0.0` одна и та же версия. Значение
  `start_vuln_version = 0` означает «с самой первой версии».
- Границы диапазона хранятся строками в таблице уязвимостей и не ссылаются на
  таблицу версий: в фиде версий нет `start_vuln_version` у 106 из 135 записей и
  `fixed_version` у 17 из 135.
- Строка таблицы уязвимостей это диапазон, а не бюллетень: в 135 записях только
  105 разных `KLA_id`, один бюллетень относится к нескольким веткам версий и
  продуктам.
- Загрузка данных это отдельная команда, таблицы создаются автоматически. Если
  база пуста, команды подскажут выполнить `load`.
- Данные только дополняются: новые версии и бюллетени можно догрузить, не
  пересоздавая базу. Дубли отсекаются ограничениями уникальности, каждый файл
  загружается отдельной транзакцией.
- Каждая запись фида проверяется (Pydantic): формат версии, дата, непустые поля,
  порядок границ диапазона. Невалидная запись пропускается с сообщением (файл,
  номер записи, поле, причина), остальные загружаются.
- SQLite не требует настройки сервера. Адрес базы задаётся переменной окружения
  `KASP_DB_URL` (по умолчанию `sqlite:///kasp.db`), доступ к данным идёт через
  SQLAlchemy, поэтому смена СУБД сводится к другому адресу и драйверу (на
  PostgreSQL проект не проверялся).

## Схема базы

| Таблица | Поля | Уникальность |
|---|---|---|
| `products` | `id`, `vendor`, `name` | (`vendor`, `name`) |
| `versions` | `id`, `product_id`, `version` | (`product_id`, `version`) |
| `vulnerabilities` | `id`, `product_id`, `kla_id`, `description`, `pub_date`, `start_version`, `fixed_version` | (`product_id`, `kla_id`, `start_version`, `fixed_version`) |

`versions.product_id` и `vulnerabilities.product_id` ссылаются на `products.id`.

## Ограничения

- Поддерживаются версии вида `1.2.3` из чисел через точки. Суффиксы (`-beta`,
  `rc1`) не поддерживаются: такие записи отвергаются при загрузке, а в команде
  `check` такая версия вызывает ошибку.
- Версия, которой нет в данных, никогда не считается безопасной: для неё
  сообщается либо список найденных уязвимостей, либо «версия не найдена».
- Поиск без учёта регистра в SQLite полностью работает только для латиницы (в
  фидах названия латиницей).
- Каскадное удаление и принудительная проверка внешних ключей SQLite не включены:
  программа только добавляет данные и ничего не удаляет.
- `kasp.db` лежит в репозитории для удобства просмотра. Если загрузить другие
  файлы, база изменится.

## Тесты и проверка кода

```
uv run pytest -q
```
25 тестов работают на базе SQLite в памяти, не зависят от файлов в `data/` и не
трогают `kasp.db`.

- `tests/test_versions.py`: разбор версий (`15` = `15.0.0`), числовое сравнение,
  строгий отказ на некорректных версиях (`1.x`, `1_0`, `+1`, пробелы, минус,
  точка в конце), границы диапазона `[start, fixed)`.
- `tests/test_queries.py`: поиск продукта (точное совпадение без учёта регистра,
  по части названия, не найден, спецсимволы), безопасные версии в числовом
  порядке, `check` для известной и неизвестной версии, порядок уязвимостей.
- `tests/test_loader.py`: загрузка фидов, повторная загрузка без дублей, пропуск
  невалидных записей с сообщением, продукт, известный только из уязвимостей.

Проверка стиля кода:
```
uv run ruff check src tests
uv run ruff format --check src tests
```
